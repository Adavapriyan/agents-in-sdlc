最初にプロジェクトに小さな機能を追加しました。より大きな変更には、もっとしっかりしたプロセスが必要です。GitHub Copilot app は組織の既存のフローに沿って作業できるように設計されており、適切な方法で適切なものを構築できます。このレッスンから数回にわたり、一般的なエージェント駆動の開発プロセスを実践します。まず Issue から新機能を作成し、コードが有効で、機能が期待どおりに動作することを確かめて、最後にプロジェクトへマージします。

> [!NOTE]
> 機能開発を続ける間、同じセッションを使います。通常は作業対象のファイルの種類ごとに異なるセッションや PR を使いますが、ここでは主な概念に集中するため手順を簡略化します。

このレッスンでは、次の操作を行います。

- GitHub Issue からエージェント セッションを開始します。
- **Plan** モードで要件を定義します。
- **Autopilot** モードで新しい機能を実装します。
- コードをレビューします。
- ブラウザー キャンバスで機能を手動で検証します。

機能の開発を続ける中で、リポジトリの指示を更新し、既存の `quality-checks` スキルをカスタマイズし、MCP による検証を追加して QA エージェントを作成し、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが増え、訪問者はカテゴリやパブリッシャーでゲームを絞り込む必要があります。バックログの Issue には機能が記載されていますが、カテゴリを組み合わせる方法など、コーディング前に合意が必要な詳細があります。Plan モードでその点を決めてから、範囲を定めた実装を Autopilot に許可します。

## 背景

AI コーディング エージェントを開発フローに取り入れても、基本は変わりません。むしろ、より重要になります。多くの開発者は、次のような流れで作業します。

1. 作業内容の詳細が記載された Issue を開きます。
2. 構築する内容を計画します。
3. コードを作成してレビューします。
4. テストを実行し、コードを検証します。
5. 新機能を手動で検証します。
6. プルリクエスト (PR) を作成します。
7. コードのレビューと継続的インテグレーション プロセスが成功したら、マージします。

> [!NOTE]
> 正確な手順はチームや組織によって異なりますが、多くの場合は上記の流れに近い手順になります。

この標準的な方法を守ることで、AI が生成したコードが要件を満たし、手作業で作成したコードと同じレビュー プロセスを通るようにできます。

## セッション モード

**セッション モード**は、エージェントの自律性を制御します。プロンプト フィールド下のドロップダウンから設定し、いつでも変更できます。

- **Interactive**: エージェントと一緒に作業します。エージェントは変更を提案し、次の操作の前に入力を待ちます。
- **Plan**: エージェントが最初に計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot**: エージェントが自律的にコードを書き、テストを実行し、入力を待たずに作業を反復します。

Plan モードで始めて計画をレビューし、Autopilot で実装します。

## Issue からセッションを開始する

フィルター機能の作業を始める前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys のリポジトリ フォルダーを選択し、リポジトリの上部ナビゲーションで **Issues** を選択します。**Allow users to filter games by category and publisher** を開きます。これはテンプレートに含まれる Issue です。新たに作成する必要はありません。
2. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選びます。

    ![GitHub Copilot app の Issue ビューで New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. Issue がセッションに添付されていることを確認し、モード セレクターで **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。ターミナルでは使えてセッションで見つからない場合は、アプリの PATH またはバージョン マネージャーの設定を確認し、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが見つけられないという理由だけで npm を再インストールしないでください。

## フィルター機能を計画する

計画することで、Copilot がコードを書く前にアプローチを確認できます。Issue から開始したため、Copilot は機能のリクエストをコンテキストとして把握しています。次を送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、Issue の受け入れ基準と計画を照らし合わせます。カテゴリとパブリッシャーによる絞り込み、アクセシブルなコントロール、データ アクセスの変更、テストが含まれていることを確認します。複数カテゴリの組み合わせ方や、該当するゲームがない場合の動作など、不明確な点を話し合います。

計画には、プロジェクトの既存ツールを使った lint、ユニット テスト、E2E テスト、型チェックを含めます。フィルター機能の実装とテストに範囲を絞り、品質ワークフローを完了してから PR を作成します。計画の修正を依頼してから承認し、後で検証できるよう Issue の URL と合意事項を控えます。

## Autopilot を明示的に承認する

計画に納得したら、**Approve and implement this plan**、または使用中のバージョンに表示される同等の選択肢を選択します。承認するとモードが自動で変わるとは限らないため、実際のモードを確認してください。モード表示が **Autopilot** になっていることを確認します。

Copilot は実装を始め、合意した計画に沿ってコードを生成し、テストを実行しながら作業を反復します。

> [!NOTE]
> 承認すると実装がすぐに始まる場合があります。先に計画をレビューしてください。依存関係が不足している、またはポートが競合していると報告された場合は、チェック完了と見なす前にセットアップの問題を解決します。停止してよいのは、自分で起動したサーバーだけです。

## 実装をレビューして検証する

生成されたコードは、他のコードと同様にマージ前にレビューします。コードを確認し、サイトを実行して問題がないか確かめましょう。

1. **Changes** を開き、フィルター機能の実装とテストを確認します。
2. 複数カテゴリとパブリッシャーの組み合わせも含め、結果を Issue と承認した追加の合意事項に照らし合わせます。変更が既存のリポジトリの指示に従っていることを確認します。
3. lint、ユニット テスト、E2E テスト、型チェックの出力を確認します。スキップされたチェックは成功ではありません。
4. 実装を承認する前に失敗を解消し、該当するチェックを再実行します。Playwright の E2E 設定はビルドしてプレビューを配信し、ローカル サーバーを再利用できます。以前のレッスンではなく、この worktree のサーバーがテスト対象であることを確認します。

## 新しい機能を確認する

コードに問題がないように見えても、実際に動くか確認しましょう。アプリを起動し、ブラウザー キャンバスでサイトを開きます。

1. 次のプロンプトで、アプリを起動してブラウザー キャンバスで開くよう Copilot に依頼します。

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザー ウィンドウが開きます。
3. カテゴリを選択し、結果が選択したカテゴリに合っていることを確認します。フィルターを解除してから、パブリッシャーを選択し、結果を確認します。
4. カテゴリとパブリッシャーのフィルターを組み合わせ、結果を Issue と承認した計画に照らし合わせます。複数カテゴリに対応している場合は、合意した組み合わせの動作を確認します。
5. 該当するゲームがない組み合わせを試し、空の状態を確認します。フィルターを解除またはリセットして、一覧全体に戻ることも確認します。
6. 確認が終わったら、次のプロンプトで、このセッションで起動した開発サーバーを停止するよう Copilot に依頼します。

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 次のレッスンのためにセッションを保持する

フィルター機能の PR は、まだ作成したりマージしたりしないでください。レッスン 4 から 8 まで、同じセッション、worktree、ブランチを使います。次はカスタム指示をフィルター機能のコードに適用し、スキルと QA の改善を追加してから、レッスン 8 でまとめた PR を作成してマージします。サーバーを停止した後、セッションを終了せずに待機状態にしておきます。次のレッスンでは同じセッションに戻ります。
